# Content integrity checks — evidence before implementation

2026-10-09. Roadmap F-CON-01 requires stable registries and content validation. Current content already lives in typed TypeScript registries; retain that source of truth and the authored town JSON. No editor, data-format migration or gameplay change is needed to add useful checks.

**Local evidence:** classes refer to primary skills, weapon/offhand bases and starter gear by string. Legendaries and set pieces refer to item bases; fields refer to zones; guardian lookups refer to monster IDs. These relationships are not enforced by TypeScript's string types. `runeUnlockLevel` and tier purchasing index separate arrays; missing entries can create undefined/NaN behavior. Gem rank lookups similarly rely on matching value-array lengths. Affix maps are generated by stat key and can silently overwrite duplicate stat entries. Existing `town:check` covers town geometry and reachability only.

**Reference context:** Runic's [GUTS introduction](https://docs.runicgames.com/wiki/Introduction_to_the_Editor), complete text read, last modified 2012-11-19, separates units, skills, affixes, sets, spawn pools and stat curves into data editing domains. This is historical workflow evidence, not a recommendation to copy its format or numerical values. Our validator rules come from actual Hearthfall consumers, not external balance targets.

**Addition:** `content:check` checks key/id agreement; missing and wrong-class references; starter equipment compatibility; finite/nonnegative base quantities; ordered min/max ranges; field and guardian links; rune/tier array indexing; gem rank lengths; duplicate local rune/affix IDs; and unresolved skill-description placeholders. Include the existing town validation in that command and verification workflow. Numeric requirements express existing structural meanings (e.g. a range minimum cannot exceed its maximum); no damage, price, timing or unlock target is selected.

**Boundaries:** TypeScript remains the structural schema for typed definitions. This is a semantic validation layer, not a parser for arbitrary untrusted JSON, behavior-flag coverage, full localization or proof of good balance. Do not rename IDs, change content, remove items, adjust combat or restyle UI to make checks pass. Any discovered defect needs its own evidence and impact record.

**Acceptance:** shipped definitions pass without data changes. Mutation fixtures demonstrate actionable paths for missing references, duplicate IDs, invalid quantities/ranges, mismatched rank arrays and unresolved placeholders. Tests must not mutate global content. A new typed definition still needs implementation, references and visual/gameplay checks. Rollback: remove the validator/command/test stage together; no saves or content change.
